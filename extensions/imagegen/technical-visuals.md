# Technical / PR illustrations

Use the default imagegen tool and save-path rules. A one-line PR-link request is enough; derive the visual brief from the source.

- Read the actual PR description, relevant changes and tests. Distinguish the reader's takeaway from implementation and validation details.
- Aim for concise but informative explanation: readers should understand the core logic in context, not just a slogan. Keep the relevant actors, relationships, conditions and changes that explain how or why it works. Large text, empty space or very few labels do not establish clarity.
- Before simplifying, identify the principal change and the other observable behaviors or prerequisites that would change how a reader uses or interprets it. Preserve those relationships even if they need a small inset or a second view. An architecture should make it possible to follow a real request or job from its entry to the data or result, with ownership visible at consequential handoffs. If several effects are fixed, show the distinct effects that matter to the reader rather than implying the first example covers them all.
- Separate research notes from visible copy, then translate the relevant mechanism into visual structure: flows, comparisons, concrete examples or other suitable forms. Reduce repetitive prose and code detail, not useful information. When necessary context would crowd one image, split into a connected sequence rather than dropping that context.
- Explain in the reader's language. Prefer short human phrases to method/class/variable names; include identifiers only when they help understanding or are requested, and preserve them accurately.
- Sketch the relationship before writing labels. Give a real object, path, state, or quantity a visible role through its shape, position, length, fill, or connection. Put short labels beside the marks they qualify. Use a concrete example when it reveals the mechanism, and identify conceptual values. Use measured results only when verified.
- When a boundary changes the meaning of the main claim, keep a short qualifier beside the relevant visual: what the signal actually establishes, whose state it represents, or which prerequisite limits it. Do not hide an essential boundary in a detached caption. Leave PR numbers, commits, sources, test records and secondary caveats outside the image.
- Design the picture around the relationship the reader needs to see. Before writing visible text, sketch the objects, their boundaries and how a reader follows them. Compare viable visual structures when useful; a branch, shared destination, nested system or aligned states may reveal more than a row of equal cards. Keep the real actors and meaningful connections in the frame.
- Give the main mechanism the most visual weight. Group supporting context around the thing it explains, use distinct silhouettes or symbols where they convey meaning, and use typography and color to clarify levels of information. Avoid generic repeated boxes or an oversized title when they compete with the story. Choose composition, density, color and figure count for the content.
- At expected display width, check whether a reader can trace the crucial relationship through the drawing itself. If the mechanism is flattened or context is missing, reconsider the composition; use localized edits for localized flaws.
- Before delivering, check the rendered image at ordinary reading size against the source. For claims about behavior, check the implementation or a focused test. Omit supplemental claims that the available evidence does not establish. Trace a representative case and any branch or boundary that changes the conclusion. Check each visual claim: object identity, arrow direction, counts, units, scale, and the distinction between changed and unchanged states. Keep rule qualifiers beside the relevant action or formula. Use a consistent scale for exact comparisons. Mark a schematic as such and preserve the relationships it illustrates. If any mark or label would lead to a wrong reading, correct the image and verify the corrected render.

## Two candidates and an independent selection

For an ordinary PR illustration, default to two independent candidates in parallel when the host supports delegation and both agents can call the built-in image tool. Honor an explicit user choice of candidate, count, or schedule.

1. Prepare one fact-only PR snapshot and the user's requirements. Give both drafting agents the same snapshot and separate output locations. Keep earlier artwork, ratings, and each other's work outside their inputs. Assign one to follow the actual object or state change and the other to compare paths or states using a shared input. Match the requested asset format in both drafts. Each drafting agent delivers one candidate and leaves orchestration to the parent.
2. Ask a separate reviewer in a fresh context to assess the rendered candidates under randomly ordered anonymous labels against the same facts. Use a 1–5 scale for factual accuracy, graphic explanation, context, and readability. Have the reviewer name any material error and point to the source evidence. For motion, require successful playback and readable state transitions. Keep generation and selection independent of completion order.
3. Honor the user's picked candidate after it passes review. With no explicit pick, select the highest average among candidates that score at least 4 on each dimension and clear the material-error and playback checks. Break ties by accuracy, graphic explanation, context, then readability. For a complete tie, use the frozen order of the two assignments above. Verify the selected file in its final location and deliver it. Offer both when the user asks for options.
4. If the selected candidate fails a check or neither qualifies, repair the relevant issue and have the corrected render independently rechecked. If the host lacks parallel delegation or the required tools in child contexts, use the same two assignments sequentially with the built-in image tool. Apply the same review checks; disclose the scope of review when a separate reviewer is unavailable.

## Motion when useful
- Use motion to reveal a meaningful sequence or change, rather than merely adding activity. Keep text, topology and object identity stable; retain a readable still. Provide pause/step controls for interactive versions where useful.
- Use native GIF only if the tool exposes it. Otherwise consider an existing local frame assembler or a small deterministic diagram/export. Match the requested format; an interactive diagram is not a GIF. When motion is optional, a good still is valid. Avoid unnecessary dependencies and silent paid-API switches.
- Verify actual format, frame count, timing and playback. Inspect registration, direction, loop seam and legibility; identify locally assembled GIFs as such.
