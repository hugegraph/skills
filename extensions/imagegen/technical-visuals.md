# Technical change illustrations

Use the default imagegen tool and save-path rules. A one-line request identifying a PR, MR, local commit set, or working-tree diff is enough; derive the visual brief from the actual change.

- Get the actual changes through an available source, such as a repository integration, a host CLI, local Git history, or a supplied patch. For GitHub, `gh` is one option. Verify the comparison or commit set matches the request and check relevant code, tests, and descriptions when available. Ask for the missing diff or source if the evidence cannot establish the change.
- For several commits, explain their combined effect on the system. Show intermediate steps only if they matter to how the change works or is used. Keep implementation and validation details separate from the reader's takeaway.
- Aim for concise but informative explanation: readers should understand the core logic in context, not just a slogan. Keep the relevant actors, relationships, conditions and changes that explain how or why it works. Large text, empty space or very few labels do not establish clarity.
- Before simplifying, identify the principal change and the other observable behaviors or prerequisites that would change how a reader uses or interprets it. Preserve those relationships even if they need a small inset or a second view. An architecture should make it possible to follow a real request or job from its entry to the data or result, with ownership visible at consequential handoffs. If several effects are fixed, show the distinct effects that matter to the reader rather than implying the first example covers them all.
- Separate research notes from visible copy, then translate the relevant mechanism into visual structure: flows, comparisons, concrete examples or other suitable forms. Reduce repetitive prose and code detail, not useful information. When necessary context would crowd one image, split into a connected sequence rather than dropping that context.
- Explain in the reader's language. Prefer short human phrases to method/class/variable names; include identifiers only when they help understanding or are requested, and preserve them accurately.
- Sketch the relationship before writing labels. Give a real object, path, state, or quantity a visible role through its shape, position, length, fill, or connection. Put short labels beside the marks they qualify. Use a concrete example when it reveals the mechanism, and identify conceptual values. Use measured results only when verified.
- When a boundary changes the meaning of the main claim, keep a short qualifier beside the relevant visual: what the signal actually establishes, whose state it represents, or which prerequisite limits it. Do not hide an essential boundary in a detached caption. Leave change IDs, commit hashes, sources, test records and secondary caveats outside the image.
- Design the picture around the relationship the reader needs to see. Before writing visible text, sketch the objects, their boundaries and how a reader follows them. Compare viable visual structures when useful; a branch, shared destination, nested system or aligned states may reveal more than a row of equal cards. Keep the real actors and meaningful connections in the frame.
- Give the main mechanism the most visual weight. Group supporting context around the thing it explains, use distinct silhouettes or symbols where they convey meaning, and use typography and color to clarify levels of information. Avoid generic repeated boxes or an oversized title when they compete with the story. Choose composition, density, color and figure count for the content.
- Before prompting, trace a representative case and any branch or boundary that changes its outcome against implementation or tests. State the visual relationships the render must preserve, such as equal lengths, ordering, fit, containment, connector endpoints, and unchanged boundaries. Use a shared scale for exact comparisons and align corresponding anchors across views. When exact geometry is unnecessary, use discrete symbols or a simpler, labeled schematic that still preserves the relationship.
- At expected display width, read the marks before their labels. Check what lengths, positions, fill, and connections imply, including object identity, arrow direction, counts, and which states changed. Then check labels, units, and qualifiers against the source, and omit unsupported claims. Inspect or measure the relevant region when a close comparison determines the outcome. A correct label or a “not to scale” note cannot rescue a picture that implies the opposite result. Repair the affected mark and recheck the whole render. If the layout keeps misleading, simplify the encoding while preserving the mechanism.

## Two candidates, both shown by default

Prepare one complete image prompt from the source and the user's request, just as for a single illustration. For a default run, use it for two independent generations and show both in the same final response. A request to run the workflow once still takes two candidates. Honor an explicit choice of candidate, count, schedule, or distinct creative directions. A request for one image uses the same preparation and one generation.

For the default two-image workflow:

1. Finalize the prompt before dispatch. Use the same exact prompt text, fixed references (if any), and generation settings for both initial calls. Use the same storyboard and timing plan for motion. Call the built-in tool independently in parallel, directly or through two fresh agents instructed to relay the prepared inputs verbatim. Use separate output paths and keep output labels and paths outside the image prompt. If needed, run the same two calls sequentially. In either mode, use the original references by explicit path, ID, or the same isolated pre-generation attachment context. If none is available, report the reference limitation. Keep each result outside the other call's context. Similar renders are valid.
2. Check each render against the source using the checks above. For motion, verify playback and readable state transitions. Repair concrete errors in the affected render and recheck it. Treat A and B as deliverables and apply the save-path rules to both, including for project-bound work. Verify both sets of files in their final locations.
3. Display both as **Option A** and **Option B** in dispatch order. Embed each image or GIF where supported and provide a direct link to each file. Describe the shared mechanism once. Skip the judge, scores, ranking, and default winner unless the user asks to evaluate or recommend. Visual preference and relative polish do not justify hiding an option. If a tool failure or unresolved material error prevents delivery after a repair attempt, report how many candidates were generated and the specific reason an option is missing.

If the user asks for a recommendation or comparative assessment, use the existing options when available. Ask an independent reviewer to compare factual accuracy, how clearly each image shows the mechanism, context, and readability. Keep both options visible and explain the trade-offs. A recommendation is advisory. Treat an option as chosen only when the user chooses it.

## Motion when useful
- Use motion to reveal a meaningful sequence or change, rather than merely adding activity. Keep text, topology and object identity stable; retain a readable still. Provide pause/step controls for interactive versions where useful.
- Use native GIF only if the tool exposes it. Otherwise consider an existing local frame assembler or a small deterministic diagram/export. Match the requested format; an interactive diagram is not a GIF. When motion is optional, a good still is valid. Avoid unnecessary dependencies and silent paid-API switches.
- Verify actual format, frame count, timing and playback. Inspect registration, direction, loop seam and legibility; identify locally assembled GIFs as such.
